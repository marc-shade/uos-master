04Hardware gates — decide before you build

Each gate is a small, cheap experiment on the real machine that de-risks an entire milestone. No code ships above a gate that hasn't closed.

Gate G1 · VDC access from user code — blocks all 80-col work

Status: open. Register reads at $D600/$D601 through direct pokes return $00/garbage both in VICE x128 and on the real hardware (probed across register dumps, with and without ready-handshake, at 40- and 80-col boot) — while the kernal's own 80-col console works. Hypothesis: the kernal reaches the 8563 through its banked-I/O or MMU I/O-page configuration rather than plain I/O-mode pokes, or a register-select subtlety.

  • Pattern-match the kernal ROM (/usr/share/vice/C128/*.bin) for AD 00 D6 / 8D 01 D6 sequences to find the kernal's own 8563 read/write routines and their exact calling convention.
  • Prove a user routine that uses those ROM entry points (or copies their recipe) touches VDC RAM and reads it back.
  • Deliverable: vdcdetect.prg prints REG18 OK on the real 80-col screen.

Consequence if closed in C64 mode: dual-display works the cheap way. If C64-mode VDC access proves impossible: the OS needs a C128-mode kernel (G6) — a much larger architectural change; that's why this gates first.

Gate G2 · Keyboard IRQ without breaking the mouse

The main loop is a busy-wait on $DC01 bit 4. A keyboard path must share the CIA1 keyboard-matrix scan with the joystick line reads (the two conflict electrically — this is the same reason GEOS 2.0's keyboard input is quirky). Approach: scan the keyboard in the existing INIT_MOUSE interrupt when a key changes state, push decoded events into a ring buffer, and have apps read the queue. Acceptance: typed characters reach an app while the pointer keeps tracking, with no CIA scan glitches visible on screen.

Gate G3 · VDC 640×200 text+bitmap mode bring-up

8563 init (registers 0–11), clear-screen at VDC RAM $0000, character-set upload (8×8 font from the chargen ROM or a custom one), fast cursor positioning. Two possible render strategies: character mode (cheap: draw with a PETSCII-like set in RAM — ideal for the file manager and terminal, a text-mode desktop like C64 OS's) vs bitmap mode (full 640×200 graphics — matches the VIC desktop's feel, 6× the RAM traffic). Character mode is the pragmatic v1; the same module exposes bitmap later.

05The build-out, milestone by milestone

Sequence is deliberate: each milestone ships something usable on the physical machine, and nothing later depends on an unverified assumption.

M0 · done

Fork & platform

complete
  • Linux build with byte-identical rebuild proof
  • Real Applications launcher (live disk scan, filtered, clickable)
  • Core FILLFILE dynamic-loading export ($0829)
  • Fork at marc-shade/uos-master, signed commits, upstream tracked

Acceptance met: launcher lists real apps on hardware and launches them.

M1 next

80 columns & the second screen

  • Close G1 (VDC access) → uos-vdc module: init, clear, character-set upload
  • VDC text output API (VPutS, VClrRect, scroll) mirroring the existing VIC macro set
  • Single-monitor switch: boot-time display selection from settings — 40, 80, both (VIC keeps rendering its plane regardless; "switch" = which gets the desktop)
  • Dual-monitor mode: VIC stays the desktop; VDC mirrors the window layer as its own 80-col surface (menus + windows rendered twice, once per screen) — the C128's two chips make this genuinely cheap: no re-render arbitration, both displays refresh independently
  • Landing zone: the uOS boot banner prints on both screens, then the desktop draws on the configured one(s)

Acceptance: with both monitors connected the desktop shows on each at its native resolution; with one monitor, a boot-time/settings switch moves it — verified on hardware at both defaults.

M2 after M1

Input, properly

  • Close G2 → keyboard event queue; apps read it
  • Pointer jitter filter (pot-sampling smoothing; Tom+ mode doc)
  • Joystick-in-port-1 as fallback pointer driver
  • Window Close/X semantics: route ON_CLOSE from title-bar clicks (currently dead code)

Acceptance: type into a dialog while the mouse keeps tracking; every window closes.

M3 the workhorse

Real applications

  • File manager: directory browser over kernal serial, scroll list, file info panel, SCRATCH, copy between drive A/B; the existing FILLFILE path launches uos-* apps from it
  • Settings: persists to the system disk (display mode, input driver, drive); adds the missing back to desktop path so apps are no longer dead-ends
  • Trash: real delete-confirm semantics with the file manager

Acceptance: rename a file, launch an app from the file manager, change a setting, hard-reset, settings survive.

M4 differentiator

Ultimate II+ integration

  • REU memory manager: 16 MB as banked RAM + native-mode RAM disks (uOS already owns bank 0–2 stashing; give apps an API)
  • 2 MHz FAST-mode regions for redraw-heavy paths (screen copies shrink ~2×)
  • U2+ REST bridge: a resident serial listener so the desktop can swap the drive-A disk image, reload fonts, snapshot screens — no other C128 OS even conceives of this; the fork's signature feature

Acceptance: swap drive images from the desktop, see the change on the U2+'s own UI.

M5 power layer

Command line & shell

  • Command-line app: line editor in a window, command table (DIR, CAT, RUN, SYS, COPY, DEL, CD), redirection into the file manager's display
  • Later: extend toward geoSHELL-style scripting

Acceptance: a full workflow — boot, list, load, run, edit a setting — completes without touching the mouse.

M6 later

Landscape & polish

  • Backdrops/desk patterns (reusing the REU banks), screen savers
  • App SDK docs: the widget macro set + FILLFILE/app conventions as a programmer's guide
  • Release discipline: versioned D64 per tag, changelog, upstream PR

06Open decisions to record

C64 mode vs C128 mode

uOS boots in C64 mode (that's why the VDC question exists — Gate G1). If G1 fails in C64 mode, a C128-mode kernel gets the VDC and 2 MHz for free but inherits MMU-kernal complexity. The launcher, file manager and most of M2–M3 work either way.

VDC: character or bitmap first

Character mode is 10× cheaper to move pixels in and matches C64 OS's text-mode bet; bitmap makes the 80-col desktop a first-class twin. Recommend: character-mode desktop on the VDC in M1, bitmap upgrade scoped for M4±.

Pointer jitter

Root causes ranked: Tom+ host-mode switch → U2+ REU bus stealing pot-sampling cycles → WIP driver sampling. Fix order: document the mode switch, add smoothing in the driver, then measure bus-time under REU traffic.

Where GEOS/MegaPatch fits

MegaPatch 3.3 r12 sits staged on drive B (install pending). It is the *complete* GEOS-family system and a working reference implementation — keep it installed as the comparison baseline, not as the fork's competitor.
