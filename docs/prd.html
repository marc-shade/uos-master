One Operating System for the Entire Modern Commodore Universe

Product requirements for UltOS as the universal OS of the 8-bit Commodore platform: every real machine, every FPGA revival, every cartridge, every accelerator shipping in 2026 — detected at boot, driven natively, and degrading gracefully to whatever is actually plugged in.

Reference hardware C128 + Ultimate II+, 16 MB REU, dual displays, Tom+ USB mouse Author fork of Scott Hutter's UltOS

VVision and product thesis

In 2026 the Commodore 8-bit world stopped being "retro" and became a platform family: Commodore itself ships an FPGA C64; the Ultimate line has become the cartridge-standard; a Raspberry Pi board emulates a 14 MHz 65816 with 16 MB of SuperRAM; Wi-Fi, Ethernet, SD and REU emulations all coexist on the same IEC bus. Every one of these machines deserves an operating system that knows what it is running on — the way desktop OSes do — instead of assuming 1982 hardware.

Product thesis: UltOS is a capability-discovering OS. At boot it probes video (VIC/8563 VDC), memory (REU/GeoRAM/65816 SuperRAM), storage (1541…1581, SD2IEC, IDE64, U2+ file system), input (1351/micromys/joystick/keyboard) and network (RR-Net/64NIC, WiC64, Meatloaf, U2+ REST), builds a capability table, and enables everything it finds — with a driver architecture where adding a platform is a driver, not a rewrite.

Why UltOS specifically: the upstream author's own 2026 project (RAD Expansion Unit) brings 65816-class acceleration to C64 and C128 — the OS and the accelerator are converging from the same source. UltOS is positioned to be the system software that the modern-accelerator generation actually runs.

AArchitecture: capability discovery, not device lists

The PRD's central requirement is not "support device X". It is: boot → probe → build the capability table → enable what exists → expose the rest at zero cost. Every subsystem declares itself to a driver registry with a capability bitmask (as of rev 1: CAP_VDC, CAP_REU, CAP_65816, CAP_NET, CAP_RTC, CAP_NATIVEFS); apps query the table, never the hardware.

FR-A1 · Boot-time hardware probe must
  • Probe order & timeouts defined; every probe idempotent and crash-safe (a hanging device must never stop boot)
  • Capability table persisted to the settings disk after each change
  • Probe results shown on the boot banner — the machine tells you what it found
FR-A2 · Driver registry must
  • Per-class drivers (video / store / ram / input / net) with uniform entry vectors
  • Drivers live loadable from disk via the core FILLFILE+APP_LOADER path — new hardware = a driver file, no reflash
  • Drivers are optional: the OS boots with zero extras and upgrades itself when it finds them

DDisplay subsystem

FR-D1 · Dual native displays must (P0)

VIC-II 40-col and 8563 VDC 80-col are independent chips: both displays render simultaneously with no arbitration. With two monitors attached, the desktop runs on both at native resolution (configurable mirror or extended roles). Gated on VDC-access Gate G1 (kernal ROM pattern-match in progress).

FR-D2 · Single-monitor switching must (P0)

Settings-selectable 40 / 80 / both; setting persists; switching requires no reboot once both drivers are resident (module load/unload at the graphics layer).

FR-D3 · Enhanced VDC modes (with 64 K VDC RAM) should

vdcmaniac v1.0.0 (2026) demonstrates on real hardware: FLI 480×252, HFLI 640×400, interlaced 640×576, mono 800×600, plus custom rasters. UltOS adopts those techniques: detect VDC RAM size (16 K vs 64 K — e.g. SaRuMan upgrade), expose hi-res desktop options only when the RAM exists, and reuse the Oscar64/Krill-loader proven patterns.

FR-D4 · FPGA video paths should (P1)

On Ultimate 64 Elite II / C64 Ultimate: use the HDMI framebuffer option (50 Hz on 60 Hz panels, Elite II fw 3.14d) and U64's native features; on TheC64, fall back to VIC-only with HDMI passthrough.

IInput subsystem

FR-I1 · Keyboard must

IRQ-decoded matrix scan sharing CIA1 with the joystick line (Gate G2); event ring buffer; full C128 keyboard (including the numeric pad and ESC/ALT/TAB) in P0.

FR-I2 · Mouse must

1351 proportional protocol (Commodore 1351, Amiga-mode-capable Tom+ / micromys / mouSTer, USB-over-DB9 adapters, and USB→1351 emulation on U64E2/C64U per fw 3.14d). Requirements: two-button, position filtering to eliminate adapter jitter, hot-plug tolerance, button-held drag (semantics already stubbed in core main_loop).

FR-I3 · Joystick as pointer should

Port-1 joystick driver as fallback pointer (verified working under GEOS 2.0 on this machine), with keyboard pointer control for keyboard-only setups.

FStorage and file system

FR-F1 · Universal serial FS must

Directory listing, open/read/write/append, load/verify, scratch, rename, copy drive→drive — all through the kernal serial abstraction so anything IEC-attached (1541…1581 real or emulated, SD2IEC, Pi1541, Meatloaf, U2+, KFF2) is automatically supported.

FR-F2 · Device inventory and hot presence must

Devices 8–11 enumerated at boot with type identification (DOS error-channel handshake); the file manager shows per-device capability; U2+ SoftIEC (bus 10) and U64 internal storage treated as first-class devices.

FR-F3 · Native-mode file systems should (P2)

CMD HD/RL, FD-2000, IDE64 and 1581-native partitions via their native command sets; 16 MB native-mode RAM disks from the REU (MegaPatch-class behavior adopted).

FR-F4 · Fastload should

Krill's-loader-style fast serial burst loads where hardware permits (vdcmaniac already ships this pattern on real C128s); JiffyDOS-rom drives detected and used only in compatibility-safe modes (GEOS folklore + our U64E2 CIA-timing findings both say JiffyDOS is a compatibility surface, not a given).

MMemory subsystem

FR-M1 · REU manager must

REU sizes 128 K–16 MB (U2+/U64/KFF2-1MB/RAD). Current fork already stashes screens (bank 0), apps (bank 1) and rects (bank 2): formalize into a banking allocator with an API for apps, RAM-disk devices, and REU-backed window buffering for fast app switching (C64 OS demonstrates 30 concurrent apps with REU backing).

FR-M2 · 65816 capability layer should (RAD present)

When the RAD (or classic SuperCPU) is detected: 14 MHz-class execution, 16 MB SuperRAM banking, native 65816 mode for heavy subsystems (file indexing, image decoding), graceful single-CPU fallback otherwise. This is the same-author synergy: uOS + RAD is the intended pairing.

FR-M3 · C128 MMU banks should (P0)

Use 128's own 256 K-equivalent MMU banking space (bank 1 etc.) for system heaps before touching REU; zero-cost on every C128.

NNetworking later (M5+)

Driver classes: U2+ REST bridge (our fork's signature: serial listener ↔ U2+ API — swap drive images, reload fonts, fetch files from the LAN without leaving the desktop), WiC64 WiFi (its C128 support makes it the P0-adjacent option), RR-Net/64NIC+ Ethernet (64net/2 fileserver protocol, CS8900A raw frames for TCP later), Meatloaf WiFi-IEC (network drives as plain serial devices). Order of value: U2+ bridge first (we own both ends), then 64net/2, then WiC64 apps.

TVerification culture

Every FR verified on real hardware before "shipped" status; the fork's discipline to date (build byte-identity proof, hardware-gated milestones, signed commits) extends platform-wide:

  • P0 regression rig = our C128 + U2+ (run_prg boot, DMA screen probes, motion recordings)
  • CI emulator rig = VICE x128/x64sc headless with screenshot + memory assertions (already in use)
  • Platform matrix spot-checks on U64E2/C64U/KFF2/RAD as hardware arrives in the lab
  • Every hardware claim in docs cites its gate — the OS's docs and the roadmap share the verification ledger

RRisks and non-goals

Risks
  • VDC access in C64 mode (Gate G1) — open; kernal ROM pattern-match in progress; decides C128-mode port need
  • REU↔pot sampling interference (pointer jitter root cause on U2+) — platform-level; may cap smoothing quality on cartridge machines
  • RAD maturity — v0.2 known video corruption/crashes on some configs; feature-flag 65816 paths until stable
  • Upstream divergence — keep increments upstreamable (small, documented, hardware-proven)
Non-goals (rev 1)
  • Preemptive multitasking — event-driven single-app model with REU app swap stays
  • 128 K “1700-only” REU optimizations — minimum supported REU is 512 K-class; smaller gets degraded features, cleanly
  • MEGA65 binary compatibility — 4510 ISA is a study, not a target
  • Graphics beyond the machine's chips (no cartridge-side GPUs) — the RAD's HDMI monitor output is the only external-video surface
